# Installation matrix safety checklist

Read ADR-0016 (file classes), ADR-0018 (one activation/acquisition engine), ADR-0020 (platform supervisors), ADR-0005 (oqto-log authority), and the current `oqto-vemr.8` tracker issue before editing install/deploy test paths.

- Name the target host, OS/architecture, scenario (`fresh` or `upgrade`), **one** setup profile, and exactly one recovery mode before privileged execution: the operator's VM snapshot reference **or** an explicitly disposable throwaway VM whose hostname matches `--disposable-vm`. A snapshot string is an operator attestation, not a verified Proxmox snapshot. The throwaway alternative means installed Oqto test state may be lost; it does not authorize changes on other hosts.
- Plan/preflight must be read-only: never run sudo, install dependencies, build, restart services, or write user/admin config. Source builds are a separate explicit development path, not the release-install matrix.
- Execute only a version/target-matched canonical release artifact with a matching checksum obtained from a **trusted independent release source**; a hash generated locally from untrusted downloaded bytes proves nothing. Reject missing or ambiguous checksums, flat legacy bundles, `.gitkeep`/hidden bin placeholders, and unsupported platforms before invoking the installer. A checksum checks integrity, not publisher authenticity; release signing remains a separate gate. Installation and rollback belong to `oqto-setup`, never a second shell implementation.
- A `fresh` scenario must refuse a pre-existing active Oqto release; an `upgrade` scenario must require one. Run personal and team on **separately reset** test hosts or throwaway VMs, not sequentially on one mutable install.
- Preserve `/etc/oqto`, `~/.pi`, other user-owned state, existing services, and pre-existing tools until the operator authorizes an isolated VM mutation. Even on a throwaway VM, inventory and back up user-owned config before replacing it. Never touch hstry or treat its data as Oqto history.
- Build prerequisites belong on the packaging host, not the install host. Ubuntu 22.04 provides Python 3.10: `scripts/lint/verify-dist-manifest.py` uses the `tomli` package there, while Python 3.11+ has `tomllib` built in. Keep any packaging-only dependency isolated from user config. Cargo's workspace version and `dependencies.toml` `[oqto]` pin must match; template and extension source commits must match the manifest pins, never moving `main` or a dirty local checkout.
- Proof includes clean install, reinstall/idempotence, explicit upgrade, failing staged artifact, rollback to the prior release, strict doctor, Pi RPC/model discovery, and sandbox/profile process tests. A command preview is not install proof.
