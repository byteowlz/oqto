# First personal install: Pi preflight (offline)

Run `python3 scripts/dist/personal-pi-preflight.py --pi /path/to/pi --agent-dir /path/to/.pi/agent --route direct` (or explicitly `--route eavs`). Add `--model ID` only to record an operator-declared selection; it is **not** verified. The script emits JSON, reads only filesystem metadata, does not start Pi, does not connect to any provider or EAVS, and never reads credential bytes. Pi's own RPC model discovery can create an empty `auth.json`; therefore it is intentionally not run on the real user profile by this preflight. Pi binary acquisition still requires the pinned checksum/version/RPC verification in `pi-runtime.sh` using its isolated temporary profile; an executable path alone is not proof of verified acquisition.

`binary_acquired` means only an executable file exists at the supplied path. `credential_file_present` is not a valid-auth assertion. Human consent, provider auth, model catalog membership and chat readiness remain unverified even with an existing auth file and declared model. Direct native Pi sign-in is a separate **user-consented** `/login` action (including Codex/ChatGPT where supported); API key and local compatible model paths are alternatives. Headless OAuth may require redirect/code paste-back into Pi itself. Pi owns `auth.json`; Oqto must not copy credentials into its browser, logs or DB. EAVS is opt-in, needs its own scoped credential and reachable gateway, and is not required on the direct route. Do not edit or overwrite existing `~/.pi` files in preflight.

After explicit provider setup on the intended runner, verify the available model, select it and exercise a real streamed Pi RPC turn and reconnect before marking chat ready. This offline inventory is **not** installation, OAuth or chat proof; it does not satisfy `oqto-vemr.9.1.3` acceptance or strict doctor. See `docs/agents/install-matrix-safety.md` and `docs/release/readiness-matrix.md` for deployment gates.
