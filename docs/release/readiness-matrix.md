Original `~/.config/oqto` was copied, compared, and moved intact into the VM test workspace. No unrelated VM services were stopped.
- Public `v0.5.0` release: published hash matches, but flat `bin/` bundle lacks canonical manifest/`immutable/bin/` and its embedded `oqto-setup` needs GLIBC_2.39; Ubuntu 22.04 has GLIBC_2.35. **Not a valid clean-install candidate**. The release workflow now refuses tag/Cargo/dependency-version mismatches before building and refuses legacy flat, frontend-missing, unsafe or non-`full` Linux bundles before publication (offline tests: three version and four artifact cases). Its current packaging step still emits a flat bundle, so **the release workflow is intentionally blocked** until it uses the canonical engine; this guard does not retroactively repair `v0.5.0` or provide signing.
- Local candidate: Cargo workspace 0.5.0 built on Ubuntu 22.04; `scripts/dist/sync.sh` used pinned template/extension commits; 30-asset dist manifest and per-artifact SHA-256 checked. The embedded installer needs only GLIBC_2.34. This proves compatibility with this test VM, **not** the declared wider Linux glibc floor or release authenticity.
- The installer now checks staged `manifest_version`, `id`, explicit `release.target = "full"`, and the eight required regular executable binary files before switching `current`; unknown files, non-executable files, symlinks, and runner-only/incomplete bundles fail even if doctor is deferred. This is **not** yet validation of all non-binary declared assets. Negative default-strict fresh install returned nonzero (service contract missing). After `oqto-vemr.3.1`, independent post-check found no `current`, `last-good`, failed stage, managed links, or `.gitkeep` in `/usr/local/bin`; prior user config was byte-identical. `oqto-setup install --doctor-strict false` succeeded only as an explicit orchestrator-deferred activation, **not** an end-to-end pass.

- Gates run: `just test-install-matrix`, `just test-setup-installed-doctor`, `just test-release-version-sync`, `just test-dist-sync-pins`, `just test-deploy-mode`, strict manifest validation, `cargo test --release -p oqto-setup` (28 unit + 5 CLI integration), `cargo clippy --release -p oqto-setup --all-targets -- -D warnings`, `cargo fmt --all -- --check`, Rust AI guardrails. ## Required before calling it a release

1. Close `oqto-vemr.9.1` and children `.9.1.1`–`.9.1.3`: provide a complete, signed, version-coherent **full** Linux artifact with frontend/backend units and a separately declared **runner-only** target without those assets. Both must have the appropriate supervisor transport, working Pi chat with a usable model/provider, preserve-first user configuration and strict target-specific doctor proof. First personal install must offer user-consented native Pi Codex/ChatGPT OAuth or another usable provider; EAVS is optional when direct Pi authentication is chosen. Runner-only does not imply chat-optional. Fresh full personal **and** team hosts remain separate gates.
2. Close `oqto-vemr.8` and `.9`: make published artifacts match the canonical manifest/installer, exercise fresh/update/rollback/uninstall and dependency installation from artifacts rather than source. Test both profiles on independently reset hosts. Treat the snapshot/`--disposable-vm` choice as operator authorization, not verification of a hypervisor snapshot.
3. Prove runner sandbox policy, effective host/supervisor capability probing (`oqto-nppq.12`), Files placement/race gates, session identity/revocation and durable reconnect before broad remote-client enrollment. The Podman supervisor checks effective `podman info` rootless status before creating directories/pods. Its read-only, expiring capability report keeps rootless discovery separate from container launch, runner sandbox, and operator policy; any missing/denied/stale gate prevents availability (10 placement unit tests, including unavailable-engine privacy/no-mutation denial). On the disposable Ubuntu VM, rootless `podman info` reported `true` and a separately authorized isolated-HOME/XDG, `--network=none --read-only --cap-drop=all` BusyBox container launched and exited successfully (`~/oqto-release-e2e/podman-rootless-canary.log`). This is **generic rootless Podman launch proof**, not a runner-image/Workspace pod proof, and it does **not** establish usable `/dev/kvm`, Docker or Kata readiness **on that Ubuntu installation**. Historical native proof exists on the Arch workstation: Kata 4.0.0 launched a guest through containerd/`ctr` with Cloud Hypervisor, completed five cold-cycle timings and guest exec tests (`oqto_refactor/docs/spikes/20260805-hypeman-microvm-spike.md`). The same spike found Podman 6.0.0 → Kata 4.0.0 runtime wiring failed; historical `ctr` proof is not proof of the current Podman supervisor integration or Ubuntu host capability. Unrestricted `cargo clippy -p oqto-placement --all-targets --offline -- -D warnings` now passes: `oqto-jrf6` boxed an internal stdout-subscription error response with regression tests for missing/non-RPC/no-channel responses and buffered/live replay. Runner (81 tests) and placement (10 tests) passed; no warning suppression. A binary on PATH or `/dev/kvm` alone does not prove runnable isolation; never downgrade multi-user placement silently. Enforce the organization SSO/MFA gate `oqto-v6hw` for Desktop, headless and WebUI human access; Pi provider OAuth, EAVS and a private overlay are not Oqto Account authentication. Tailscale, Headscale and NetBird are optional connectivity recommendations (`oqto-qdxv`), not shipped dependencies or grants. Keep Mac Studio live runner unchanged without explicit operator grant.
4. Run clean native macOS and Windows GUI/install/update/uninstall tests on VMs, including distribution signing/Gatekeeper for macOS and native Windows packaging. No VM evidence means **blocked**, not passed.
