Original `~/.config/oqto` was copied, compared, and moved intact into the VM test workspace. No unrelated VM services were stopped.
- Public `v0.5.0` release: published hash matches, but flat `bin/` bundle lacks canonical manifest/`immutable/bin/` and its embedded `oqto-setup` needs GLIBC_2.39; Ubuntu 22.04 has GLIBC_2.35. **Not a valid clean-install candidate**.

The embedded installer needs only GLIBC_2.34. This proves compatibility with this test VM, **not** the declared wider Linux glibc floor or release authenticity.
- Negative default-strict fresh install returned nonzero (service contract missing). After `oqto-vemr.3.1`, independent post-check found no `current`, `last-good`, failed stage, managed links, or `.gitkeep` in `/usr/local/bin`; prior user config was byte-identical. `oqto-setup install --doctor-strict false` succeeded only as an explicit orchestrator-deferred activation, **not** an end-to-end pass.
- Upgrade with deferred doctor advanced `current` and `last-good` to the next candidate. A deliberate strict-doctor failure on the following candidate returned nonzero, restored the prior release and all eight entrypoints, and removed the failed stage. Reinstall of the active release ID refused to overwrite it; content-aware idempotence is still unimplemented. Clean uninstall was not exercised (no `oqto-setup uninstall` contract yet).
- Gates run: `just test-install-matrix`, `just test-setup-installed-doctor`, `just test-release-version-sync`, `just test-dist-sync-pins`, `just test-deploy-mode`, strict manifest validation, `cargo test --release -p oqto-setup` (28 unit + 5 CLI integration), `cargo clippy --release -p oqto-setup --all-targets -- -D warnings`, `cargo fmt --all -- --check`, Rust AI guardrails. An initial real pinned Pi 0.80.10 clean-host probe discovered zero models and incorrectly refused to install the binary before provider login could happen. After separating binary verification (checksum, version, successful RPC response) from post-login model/chat readiness, a native Ubuntu 22.04 rootless install promoted verified Pi 0.80.10 into an isolated scratch runtime with zero models; its real user `auth.json` remained absent. This is **binary availability only**, not OAuth, usable model, or chat proof (`oqto-vemr.9.1.3`).

## Required before calling it a release

1. Close `oqto-vemr.9.1` and children `.9.1.1`–`.9.1.3`: provide a complete, signed, version-coherent **full** Linux artifact with frontend/backend units and a separately declared **runner-only** target without those assets. Both must have the appropriate supervisor transport, working Pi chat with a usable model/provider, preserve-first user configuration and strict target-specific doctor proof. First personal install must offer user-consented native Pi Codex/ChatGPT OAuth or another usable provider; EAVS is optional when direct Pi authentication is chosen. Runner-only does not imply chat-optional. Fresh full personal **and** team hosts remain separate gates.
2. Close `oqto-vemr.8` and `.9`: make published artifacts match the canonical manifest/installer, exercise fresh/update/rollback/uninstall and dependency installation from artifacts rather than source. Test both profiles on independently reset hosts. Treat the snapshot/`--disposable-vm` choice as operator authorization, not verification of a hypervisor snapshot.
3. Prove runner sandbox policy, effective host/supervisor capability probing (`oqto-nppq.12`), Files placement/race gates, session identity/revocation and durable reconnect before broad remote-client enrollment. The first Podman supervisor guard now checks effective `podman info` rootless status before creating directories/pods (5 placement unit tests, native disposable Ubuntu reported `true`); it does **not** establish container launch, usable `/dev/kvm`, Docker or Kata readiness. Targeted placement Clippy `--no-deps -D warnings` passed, but the unrestricted gate remains red on an untouched `oqto-runner` large-Err warning (`oqto-jrf6`); no waiver or warning suppression is accepted. A binary on PATH or `/dev/kvm` alone does not prove runnable isolation; never downgrade multi-user placement silently. Enforce the organization SSO/MFA gate `oqto-v6hw` for Desktop, headless and WebUI human access; Pi provider OAuth, EAVS and a private overlay are not Oqto Account authentication. Tailscale, Headscale and NetBird are optional connectivity recommendations (`oqto-qdxv`), not shipped dependencies or grants. Keep Mac Studio live runner unchanged without explicit operator grant.
4. Run clean native macOS and Windows GUI/install/update/uninstall tests on VMs, including distribution signing/Gatekeeper for macOS and native Windows packaging. No VM evidence means **blocked**, not passed.

The proposed WebMCP-guided public landing page (`oqto-a8wr`) may explain deployments and export a validated secret-free draft, but the target host still runs the authoritative `oqto-setup` plan/apply with operator approval.
