# Runner-owned filesystem grants on authenticated network connections

Status: proposed. Tracks `oqto-8x3p.5`; extends ADR-0024 and ADR-0047. This is a staged implementation, **not** remote Session admission.

## Decision

Mutual TLS identifies a connection; it does not authorize every runner command. A network connection with no runner-side Files roots accepts only Ping, GetCapabilities, and the separately configured HistoryRead and ProviderLogin capabilities. All other requests, including shutdown, process control, Pi commands, streaming subscriptions, App operations and Files, are denied **before** special-case dispatch or side effects. New protocol variants are denied by default. Local Unix socket access remains governed by its OS socket boundary; this change does not reclassify local Accounts or grant network clients local authority.

For a dedicated single-user runner, the operator can pass repeated `--remote-file-root /absolute/canonical/path` arguments **and at least one** `--remote-client-cert-sha256 <64-hex-digits>` to the supervised mTLS process. Compute each pin over the enrolled client's DER leaf certificate, not its CA or PEM text. These are **supervisor-owned startup grants**, not fields in agent-editable `~/.config/oqto/config.toml`; modifying that config must never mint Files authority. A CA-valid but unpinned peer receives only inventory (and independently configured login/history capabilities). Unix socket access never inherits a TLS pin. The runner refuses root flags without `--listen-tls`, opens each root as a capability directory, rejects invalid/noncanonical/missing roots, and resolves mediated Files requests relative to these handles. No root is inferred from `HOME` or `local.workspace_dir`; relative requests and `..` are rejected. cap-std confines symlink traversal and mutations to the opened directory, including on macOS and Linux. Bounds on file read/write, directory listing and concurrent blocking filesystem workers prevent unbounded responses; only regular files are read/written and Unix opens are nonblocking to avoid hanging on FIFOs. The hub's `RemoteExecutionGrant.roots` remains a **second**, narrower gate when the hub mediates a request; a network client cannot borrow a hub Account identity merely by presenting a client certificate.

A root of `/` is intentionally permitted and means all paths the runner's **OS principal** can access, including SSH keys, runner credentials and Oqto state. A home-directory root includes home secrets. **There is no reliable default deny-list within a broad root.** A path-string deny-list can be bypassed via an in-root symlink or a race unless enforced by a separate OS/filesystem boundary. Use multiple narrow roots to exclude secrets, or run the runner under a separate low-privilege Principal with only intended access. Do not advertise `~` as "home minus credentials." The server warns when a configured root contains the entire home directory.

`--remote-file-root` alone authorizes **only mediated Files operations**, not shell, process spawn, App operations, or Pi Sessions. Merely checking a process's `cwd` does not confine the process: its shell/tools can open absolute paths, and the sandbox policy is a separate boundary. The separate supervisor flag `--remote-full-principal-pi` requires an explicit `/` Files root and a dedicated single-user runner. It admits Pi commands, PiBash, subscriptions and canonical workspace chat reload under the runner's OS principal, while generic process spawn, App operations and shutdown remain denied. Only explicitly pinned client certificates have that single user's Pi authority. Different pinned clients are **not yet isolated from each other's Pi Session IDs or history**; pinning provides admission and whole-client startup/restart revocation, not per-session ownership. Do not enroll an independent or untrusted client until session ID binding and revoke tests pass. The existing Pi sandbox, if configured, still constrains the spawned agent; the flag does not pretend that a narrow work root is process containment. Future **narrow-root** network execution must bind each process/session to a runner-enforced, OS-backed sandbox policy compatible with its root grant (Seatbelt on macOS, Linux bwrap/Landlock, a Windows implementation separately). Session-ID follow-up commands must bind to the initially admitted execution scope and revoke together; no text/index-based session reconciliation.

## Rollout and proof

The network gate and capability Files path can land without enabling direct chat. On upgrade, existing Mac Studio inventory/history/provider-login remain available if separately configured; arbitrary file and Pi access are **denied** until the operator adds supervisor flags. Narrow Files roots do not admit any Pi process. The existing dedicated Mac runner service/config are not changed by this ADR. Provision by backing up and diff-reviewing only the service definition (launchd/systemd), then restart the service to revoke prior grants. On graceful runner shutdown, the Pi manager closes active processes; do not hot-reload roots or pins without per-connection and active-session revocation semantics. Keep private-key and supervisor files outside agent sandbox access; the trusted startup arguments themselves must not be agent-editable. Preserve old runner binary/config for rollback; never widen a failing grant to `HOME`.

Before any Desktop Files or chat action is enabled, prove native macOS, Linux, and Windows behavior separately, plus authenticated live in-root positive, `.ssh`/outside-root negative, `..`, relative paths, symlink swap, root-path swap, process-command bypass, configuration failure and revocation/reconnect. Kani may prove **pure policy predicates** but cannot prove cap-std syscalls, subprocess sandboxing, or certificate enrollment. The present Files implementation does not establish the future process/session proof and is not a release/deployment gate for remote chat.
